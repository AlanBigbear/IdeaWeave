# GitHub 自动部署配置

这套流水线只自动更新代码、构建镜像和重启服务，不会执行 SQL、数据库迁移、数据导入或数据清理

线上使用 SQLite，而上游数据库交付内容是 MySQL。检测到数据库模型、数据库初始化、迁移脚本、SQL 文件或数据目录相关变更时，自动部署会停止，整个版本转为人工处理，不提供自动部署绕过开关

## 部署流程

- 拉取请求：运行后端测试、前端构建和生产镜像构建，不连接生产服务器
- 普通代码合并到 `main`：检查通过且不涉及数据库时自动部署
- 涉及数据库的合并：停止自动部署，数据库适配和对应版本部署均由人工处理
- 部署失败：健康检查失败时恢复部署前运行镜像；数据库文件不会被脚本修改

## GitHub 配置

在仓库“设置 → 环境”中新建 `production` 环境。建议为环境增加审批人，首次试运行时可以先保留审批，确认稳定后再决定是否取消

在 `production` 环境中配置以下变量

| 名称 | 必填 | 当前服务器建议值 | 说明 |
| --- | --- | --- | --- |
| `DEPLOY_HOST` | 是 | `124.221.48.238` | 服务器地址 |
| `DEPLOY_USER` | 是 | 当前可登录且能运行 Docker 的用户 | SSH 用户 |
| `DEPLOY_PORT` | 否 | `22` | 未配置时使用 22 |
| `DEPLOY_PATH` | 否 | `/opt/ideaweave` | 未配置时使用该路径 |

在 `production` 环境中配置以下密钥

| 名称 | 内容 |
| --- | --- |
| `DEPLOY_SSH_KEY` | 对应部署用户的 SSH 私钥全文 |
| `DEPLOY_KNOWN_HOSTS` | 已核验的服务器主机公钥记录 |

生成专用密钥时不要设置交互式口令，并只把公钥加入服务器部署用户的 `~/.ssh/authorized_keys`

```bash
ssh-keygen -t ed25519 -C "ideaweave-github-deploy" -f ./ideaweave-github-deploy
```

从可信网络读取主机公钥，并与当前已信任连接显示的指纹核对后，把完整输出保存为 `DEPLOY_KNOWN_HOSTS`

```bash
ssh-keyscan -H 124.221.48.238
```

部署用户需要满足以下条件

- 能读取并快进更新 `/opt/ideaweave`
- 能运行 `sudo docker` 与 `sudo docker compose`，且流水线执行时不会等待输入密码
- 服务器已安装 Git、Docker Compose、curl、flock
- `/opt/ideaweave/.env` 已存在，并继续由服务器人工维护，不放入 GitHub

## 首次试运行

1. 合并本次流水线改动到上游仓库 `main`
2. 完成 `production` 环境的变量与密钥配置
3. 打开 GitHub“操作 → 代码检查与生产部署 → 运行工作流”
4. 等待测试、镜像构建、生产部署和三个健康检查全部通过
5. 访问 `http://124.221.48.238` 与 `http://124.221.48.238:8080` 验证页面

## 数据库变更的人工流程

数据库相关改动合并后，流水线会明确失败并停止部署。由于需要把 MySQL 交付人工适配到线上 SQLite，此时整个版本按以下步骤处理

1. 由人工审核数据库变更内容和备份方案
2. 人工备份并执行所需数据库操作
3. 人工验证数据库结构和数据
4. 人工部署并验证对应代码版本
5. 确认线上实际运行版本后，人工把 `/opt/ideaweave/.deploy-state/runtime_commit` 更新为该版本的完整 Git 提交哈希

状态文件只用于告诉后续纯代码自动部署从哪个已确认运行版本开始比较，不能提前填写，也不会执行数据库操作
